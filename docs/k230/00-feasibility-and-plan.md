# K230 视觉跟踪 / 云台机械臂 / 语音 / 全屋监控：可行性与实施计划

> 阶段：可行性评估（P0 前置）。本文只定方向与分期，不含代码。
> 结论先行：**整体可行，但单块 K230 不可能同时承担全部功能，必须分期 + 分层。**

## 0. 结论摘要

| 能力 | 评级 | 一句话 |
| --- | --- | --- |
| 人脸检测 / 跟踪 | ✅ 直接可做 | 官方例程 + MOT 模块 |
| 人脸识别（1:N） | ✅ 可做 | SDK 有 face_recognition POC |
| 画面内相对坐标 | ✅ 直接可做 | 纯几何 |
| **绝对坐标** | ⚠️ 有条件 | 单目无深度，需标定 + 平面假设，或加深度相机 |
| 串口控制云台 | ✅ 直接可做 | UART API 完善 |
| 串口控制机械臂 | ⚠️ 有条件 | 取决于舵机协议与运动学 |
| 多物品检测 | ✅ 可做 | YOLOv8 例程，类别受模型限制 |
| 关键词唤醒 | ✅ 直接可做 | 官方离线 open_kws，KPU 推理，~0.3 s |
| 语音识别（ASR） | ⚠️ 只能云端 | K230 跑不动本地 ASR |
| 语音合成（TTS） | ⚠️ 云端或预录音 | 同上 |
| API 接入 | ✅ 可做 | HTTP/HTTPS/WebSocket 全有 |
| 全屋监控 | ⚠️ 需多节点 | 单板单摄像头，覆盖不了一屋 |
| 注视感知 | ⚠️ 需自研 | 有第三方实践，官方无 CanMV 例程 |
| 桌面整理（抓取归位） | ❌ 长期 | 手眼标定 + 运动规划 + 夹爪，单板不够 |

**一句话**：视觉+云台闭环半年内能做出效果；语音必须借云端或自建服务端；绝对坐标是最大的技术债；桌面整理是终局目标，不是第一期目标。

## 1. 平台事实（已核实）

来源：[K230 数据手册](https://www.kendryte.com/k230/en/v1.7/00_hardware/K230_datasheet.html)、[CanMV K230 文档](https://www.kendryte.com/k230_canmv/zh/main/index.html)。

- **CPU**：2× RISC-V C908。CPU0 800 MHz（64GCB），CPU1 1.6 GHz（带 RVV 1.0 向量扩展）
- **KPU**：INT8 / INT16。典型性能 ResNet50 ≥ 85 fps、MobileNetV2 ≥ 670 fps、**YOLOv5s ≥ 38 fps**（@INT8，整片 KPU）
- **内存**：LPDDR4 最大 2 GB（开发板常见 1 GB 版本，选型时要确认）
- **视频输入**：3× MIPI CSI，最多三路 2-lane 或 4-lane + 2-lane
- **ISP**：8 MP@30 fps；**编码**：H.264/H.265 最高 8 MP@20 fps
- **DPU**：结构光深度计算单元（可接深度模组）
- **CanMV MicroPython 外设**：UART、PWM、I2C、SPI、ADC、Timer、WDT、RTC、USB HID
- **多媒体**：Sensor、Display、Audio、Media、VENC、RTSP、WebRTC、MJPEG、MP4、Player、LVGL
- **AI**：nncase_runtime + AI Demo Pipeline（YOLO、Ai2d、MOT、Utils）
- **图像**：OpenMV 图像处理、OpenCV、cv_lite

### 已存在的官方例程（决定可行性的关键）

| 例程 | 意义 |
| --- | --- |
| [开放词汇关键词唤醒](https://www.kendryte.com/k230_canmv/zh/main/example/ai/open_kws_app.html) | 离线、KPU 推理、现场注册唤醒词、最多 8 个、~0.3 s 延迟、160 ms 一块 |

这四条说明：**人脸、检测、唤醒、语音对话都有官方起点**，不需要从零训练模型。

## 2. 三个真正的难点

### 2.1 绝对坐标（最大不确定性）

K230 默认是**单目**，单个像素无法直接得到距离。三条路线：

| 方案 | 原理 | 精度 | 成本 | 适用 |
| --- | --- | --- | --- | --- |
| A. 已知尺寸法 | 物体真实尺寸 + 焦距 → 距离 | 差（±20%+），依赖目标尺寸准确 | 零 | 人脸（用瞳距/脸宽先验）粗测距 |
| B. 平面单应 | 标定桌面/地面平面，像素 → 平面坐标 | 中（1–3 cm，取决于标定与视角） | 低 | **桌面物品、地面人员定位** |
| C. 加深度 | 结构光（DPU）或 USB ToF | 好（mm–cm 级） | 中高 | 抓取、避障 |

**建议**：第一期走 **B**，因为目标场景（桌面物品登记、人员位置）本来就落在平面上；等要做精细抓取时再上 C。

必须先做的标定：
1. 相机内参（棋盘格）
2. 相机外参（相对云台零位）
3. 平面单应（桌面/地面）
4. 云台角度 → 坐标系旋转的映射

> 注意：如果相机装在云台上、机械臂固定，那么抓取还需要**手眼标定**（eye-to-hand），这是 P3 的核心工作量。

### 2.2 语音链路

K230 的 KPU 跑不动可用的本地 ASR。两条路线：

| 路线 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 小智云端 | 直接用官方例程 | 一周内能对话 | 依赖第三方服务与网络，激活/隐私受限 |
| B. 自建服务 | K230 只做录音(Opus)+播放，PC/树莓派跑 Whisper/FunASR + Piper TTS | 可控、可离线局域网、可接自己的 LLM | 多一台设备，需自己搭服务 |

**建议**：先用 A 验证交互链路，稳定后迁移到 B。TTS 还有第三条兜底：预录音 + 拼接，零依赖。

### 2.3 算力与内存预算

KPU 是**独占资源**，人脸、YOLO、KWS 三者不能同时满帧。必须做**状态机分时**：

```
待机  →  KWS（极低算力，160ms/次）
唤醒  →  人脸检测+识别+跟踪（高帧率）
物品任务 →  YOLO 检测（高算力，降帧率）
监控  →  编码推流（占用 VENC，不占 KPU）
```

内存方面：1 GB 版本同时挂人脸 + YOLO 两个模型会紧张，建议确认板子版本，必要时选 2 GB。

## 3. 架构建议

```
┌──────────────── K230（边缘实时层）────────────────┐
│ camera → 预处理(Ai2d) → 模型(KPU) → 坐标变换      │
│                    ↓                              │
│        状态机调度（KWS / 人脸 / YOLO）              │
│                    ↓                              │
│   UART → 云台舵机    UART → 机械臂    UVC/RTSP 推流│
└───────────────────────┬───────────────────────────┘
                        │ WiFi/LAN
┌───────────────────────┴───────────────────────────┐
│ 服务层（PC / 树莓派，可选但建议）                    │
│ ASR / LLM / TTS / 物品登记数据库 / Web 面板 / 录像  │
└───────────────────────────────────────────────────┘
```

**关键决策**：K230 只负责「看得见、算得快、控得准」；重服务放外面。这样换模型、加功能都不会被板子算力卡死。

## 4. 分阶段计划

### P0 环境与基线（约 1 周）

- 交付：开发板 + 摄像头 + 云台/机械臂 + 麦克风/扬声器的实际型号清单；跑通 5 个官方例程（camera、UART、audio、YOLOv8、open_kws）
- 验收：能在 VSCode CanMV 插件里改一行参数并看到效果；串口能收到板子输出
- 风险：板子版本与内存、固件版本、驱动

### P1 视觉与坐标（约 2 周）

- 交付：人脸检测 + 跟踪（ID 稳定）；像素 → 归一化相对坐标；相机内参/外参/平面单应标定脚本与标定结果；单目测距误差实测
- 验收：目标在画面中移动，输出的归一化坐标与实际位置单调对应；桌面标记点定位误差 < 3 cm
- 风险：光照、遮挡、多人场景下的 ID 跳变

### P2 云台跟踪闭环（约 1 周）

- 交付：串口舵机协议封装、PID 控制器、死区与限速、延迟补偿
- 验收：人走动时目标保持在画面中心 ±5% 区域内；不抖动、不过冲
- 风险：Python 调度抖动；舵机供电噪声

### P3 机械臂（约 3–4 周）

- 交付：手眼标定、逆运动学、抓取点估计（桌面平面 + 物体高度）、简单轨迹
- 验收：对固定位置的已知物体完成 10 次抓取，成功率 ≥ 80%
- 风险：**这是全项目最重的一段**，硬件精度与标定质量决定上限

### P4 语音（约 2 周）

- 交付：离线关键词唤醒；ASR + TTS 链路（先用小智验证，再评估自建）；语音→视觉联动（喊名字→转头锁定）
- 验收：说唤醒词 0.5 s 内响应；一句话指令能触发「看一下」「转过去」这类动作
- 风险：云端服务可用性与合规；离线 ASR 在 K230 上不可行

### P5 多节点监控（约 2 周，可选）

- 交付：单板 RTSP/MJPEG 推流；多 K230 或「K230 + 网络摄像头」组网；Web 面板
- 验收：局域网内两路以上视频可同时观看
- 风险：带宽、内存、多节点时钟同步

### P6 桌面整理（长期，不建议排期）

- 依赖 P1 的绝对坐标 + P3 的抓取能力
- 真正的门槛不是识别，而是**抓取规划与失败恢复**

## 5. 需要你确认的信息（阻塞 P0）

1. **开发板具体型号**：CanMV-K230（1 GB / 2 GB）、K230D-Zero、庐山派、01Studio？
2. **摄像头型号**（GC2093 / OV5647 / 其他）与支架形式
3. **云台**：舵机型号、总线协议（PWM 还是串口总线舵机）、供电方式
4. **机械臂**：自由度、舵机型号、是否已有控制板与协议文档
5. **麦克风 / 扬声器**：板载还是外接
6. **是否有 PC / 树莓派**可做服务层
7. **目标场景**：全屋监控是几个点位？优先哪个房间？

## 6. 风险清单

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 单目绝对坐标误差大 | 抓取失败 | 先平面单应，必要时加深度 |
| KPU 分时导致帧率骤降 | 跟踪卡顿 | 状态机 + 降分辨率 + 只在实际需要时跑重模型 |
| 1 GB 内存不够 | 崩模型 | 确认型号；或选 2 GB 板 |
| 云端 ASR/TTS 依赖 | 断网即哑 | 双路线，尽快评估自建 |
| MicroPython 实时性 | 控制抖动 | 控制频率压到 30–50 Hz，避免在 Python 里跑重计算 |
| 硬件（舵机/机械臂）精度 | 抓取上限 | 先做视觉与云台，机械臂单独评估 |
