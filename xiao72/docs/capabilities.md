## 一、我是什么

我是一个**能写代码、能推理、能自我验证的实习生**，但有两个硬限制：

1. **我没有手**。碰不到你的硬件、量不了电压、闻不到焦味。
2. **我可能是错的**。我会给出看起来很有道理但实际编译不过的代码。

所以正确的用法不是"我告诉我答案"，而是"**我们一起做实验**"。

## 二、我强在哪（这四类事，交给我是划算的）

| 类型 | 例子 | 为什么给我做 |
|---|---|---|
| **写代码** | 固件、上位机、脚本、工具 | 快，且能自测 |
| **设计协议/架构** | 分层、帧格式、状态机 | 不受体力限制，能一次看全 |
| **算参数** | 电阻、频率、寄存器、标定矩阵 | 不会算错（会算错时也会自检） |
| **读错误推断** | 编译报错、串口乱码、现象描述 | 能穷举可能原因并排序 |
| **做工具** | 可视化教学台、模拟器、验证脚本 | 一次投入长期用 |

**判断标准**：这件事**能不能在纯信息层面完成**？能，就交给我。

## 四、怎么问，我才能一次做对（最重要的实操技能）

### 提需求公式

```
[现状] 硬件/软件已经是什么
[目标] 我要看到什么现象
[约束] 不能用什么、必须满足什么
[现象] 已经试过的、报错原文、实际 vs 期望
```

### 反例 vs 正例

**❌ 低效**
> "帮我控制一下灯"

**✓ 高效**
> "STM32F103C6 标准库，灯在 PA0（TIM2_CH1），PWM 周期寄存器设的 100。
> 我要串口输入 0-100 控亮度，且呼吸时能同时收命令。
> 现在串口能通，但灯不亮，代码和接线如下……"

### 每次问硬件问题前，准备好这 5 条

1. 板子型号
2. 接线（哪个脚 → 什么元件 → 接到哪，含电阻、共地）
3. 供电方式
4. 完整代码 + 完整报错
5. 期望现象 vs 实际现象

## 五、我的自检清单（你也可以用来验收我）

我交付代码后，你应该能回答：

- [ ] 这段代码**编译过**了吗？（我该说"已编译"）
- [ ] 有**测试**吗？测试**跑绿**了吗？
- [ ] 如果它错了，**错在哪一层**能定位吗？
- [ ] 它**失败了会怎样**？（亮着？灭了？乱动？）
- [ ] 我要怎么**独立验证**它，而不是只信我？

> 本次交付的 `verify.py` 就是第 3、5 条的答案：
> 它让"两端不一致"这种最难查的问题，在 PC 上就暴露。

## 六、你该建立的两个习惯

**习惯 1：永远先要"最小可验证版本"**
不要让我一次写 500 行。先要"能让灯亮 10 行"，跑通再加。

**习惯 2：让错误尽早、尽量便宜地发生**
- 便宜的错误：PC 上编译失败、测试红
- 贵的错误：烧到板子上、烧了硬件、机械臂乱动

**我在做的事，本质是把你犯错的成本从"贵的"挪到"便宜的"。**

## 七、合作中已经暴露的真实案例（教学价值最高）

| 事件 | 教训 |
|---|---|
| 你贴的呼吸代码 `for (l = 100; l <= 100; l--)` | 看代码看不出，跑一下就暴露 |
| 中文引号写进 JS 字符串，把代码截断 | 人写的和机器解析的是两回事 |
| 我一直在编译**自己插入的调试副本**，导致调试 8 轮都在看旧代码 | **先确认你测的是不是你以为是的那份** |
| Python 发 `L050200`、C 要求 `L`+6 位数字，两端不一致 | 这就是为什么必须写**跨端一致性测试** |

> 第四条是最值钱的：**两个人（或两个模块）各自"看起来对"，合起来就是错的。**
> 这类 bug 不靠聪明，靠测试。
