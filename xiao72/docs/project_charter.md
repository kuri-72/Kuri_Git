## 1. 长期愿景（原始需求，逐字记录）

> "做一个智能助手，识别我的语音命令，接入我的硬件，用我的函数控制我的 AI 助手专用显示器显示聊天文本 / 音箱语音输出 / 摄像头云台机械臂 / 图像识别（或用 K230 返回识别信息），帮我完成语音互动解决工程问题；利用云台机械臂和摄像头监控房间，完成物品查询、人脸识别、生物识别（猫）、记录进入次数时间和行为，利用机械臂控制加图像识别构成闭环完成桌面整理。"

## 2. 必须提前承认的边界（现在写，避免以后自我欺骗）

**R9 和 R10 是这类项目最常见的坟墓**，原因不是技术不可能，而是：

| 陷阱 | 具体表现 | 现实后果 |
|---|---|---|
| **"行为"没有定义** | "记录行为"可以是"他来了"也可以是"他在喝水" | 永远做不完，且无法验收 |
| **手眼标定被低估** | 相机坐标 → 机械臂坐标的变换，误差随距离放大 | 桌面整理需要亚厘米级精度 |
| **抓取规划不是调包** | 物体位姿估计 + 碰撞避免 + 力控 | 单这一项就是一篇论文的量级 |
| **多目标跟踪** | 猫在动、人在动、遮挡、重识别 | 学术级难度，非玩具级 |
| **实时性 vs 云端** | 云端大模型延迟 0.5–2s | 机械臂不能靠云端闭环 |

### 结论：R10（桌面整理）**现在不应作为目标**
建议降级为"未来可选实验"，且必须先满足：
1. 固定相机 + 固定臂基座的标定误差 < 5mm
2. 只整理**已知类别 + 固定摆放位置**的物品
3. 全程有人监督，有物理急停

## 3. 分阶段路线（建议，未确认）

```
阶段 A  灯控链路（进行中，已完成 v0.1）
        文本 → 意图 → 帧 → 单片机 → PWM
        目的：验证"分层 + 兜底"这套骨架

阶段 B  加安全兜底
        超时熄灭、板子 ACK、断线重连

阶段 C  换意图层 + 加语音
        规则 → LLM → ASR/TTS
        接口不变，只换输入输出

阶段 D  第一类执行器扩展：舵机
        云台 2 轴（比机械臂简单，风险可控）
        这一阶段会把"执行器抽象"真正压出来

阶段 E  视觉只做"看得见"
        摄像头画面显示 + K230 回传识别结果
        不做闭环控制，先只观察

阶段 F  闭环（谨慎）
        先做"看 → 说"，不着急"看 → 动"
```

**关键原则**：每个阶段都必须"能演示、能停止、能降级"。
不允许出现"必须整个系统跑起来才知道有没有用"的阶段。

## 4. 决定不做什么（Negative Scope）

明确写下**不做**，比写下做什么更重要：

- ❌ 不做无监督的全屋机器人（成本与安全都不现实）
- ❌ 不用云端模型做实时运动控制
- ❌ 不碰强电（220V 负载必须用成品模块 + 隔离）
- ❌ 不在没有物理急停的情况下让机械臂自动运动
- ❌ 不追求"像人一样对话"，追求"能用、可预期"

## 8. 系统的逻辑分层（2026-10-24 由 KURI72 明确定义）

> **重要定位**：点灯只是**语音控制设备的技术验证载体**，不是最终目标。
> 最终要控制机械臂、显示器等多个模块，并完成"理解—回答—执行"的完整交互。

### 8.1 四层结构

| 层 | 职责 | 候选实现 | 当前状态 |
|---|---|---|---|
| **① 唤醒** | 决定"什么时候开始听" | 唤醒词 / 物理按键 / **注视感知（K230）** / 音量阈值 | ❌ 未做（现在是一直监听） |
| **② 输入** | 拿到用户的话 | 麦克风（VAD 切句）、文字输入 | ✅ P0/P2 已完成 |
| **③ 理解 → 输出命令** | 把话变成结构化意图 | 云端 API（DeepSeek）、本地大模型（4090 那台机器） | ✅ P1/P3 已完成（灯域） |
| **④ 控制** | 执行到具体设备 | 显示器、机械臂、夜灯、未来更多模块 | ⚠️ 只有夜灯（PWM+OLED） |

### 8.2 交互主流程

```
唤醒（词/键/注视/音量）
   ↓
接收我的问题
   ↓
思考（理解意图）
   ↓
   ├─ 识别到明确的设备控制意图 → 生成命令 → 执行
   └─ 无控制意图 → 正常聊天 / 解决问题 → 语音播报 + 屏幕输出
   ↓
语音播报（TTS）+ 显示器输出文本
```

### 8.3 控制层的核心原则（KURI72 原话）

> "各模块各司其职，**有自己协议的命令则执行，无则保持**。"

技术含义（对应到已有实现）：

- 每个模块**自己声明**支持哪些命令、当前状态是什么
- 一次交互只更新被提到的模块，**没提到的模块保持原状态**
- 这与我们已验证的 **"全量状态帧"** 设计一致：
  `[L00502000|A---|]` 里 `A---` 就是给机械臂预留的占位
- 所以扩展新模块时：**加一个新的段 + 一个状态结构**，不动已有模块

### 8.4 由此产生的架构要求（尚未实现）

1. **设备注册表**：每个模块（灯/臂/屏）注册自己的命令集与状态，
   替代现在 `pipeline.py` 里写死的 `LedState`。
2. **意图路由**：区分"设备控制"与"闲聊问答"两条路径。
   现在 `intent_prompt.md` 强制只输出 4 种 JSON 命令，
   闲聊会被判成 `unknown`——**需要新增 chat 路由**。
3. **唤醒层插入点**：`pipeline.run()` 的循环开头，
   等待唤醒后才开始 `record_utterance()`。
4. **多模态输出**：TTS 播报 + 专用显示器文本。显示器是 **HDMI 副屏、由上位机直接渲染窗口**（不是独立设备、不走串口协议），只用于监视 API/本地模型输出的文字，**不引入额外延迟**。
5. **模型可选**：云端 API 与本地大模型（4090 机器）通过同一 Provider 接口切换。

| 已完成 | 在新分层里的位置 | 可复用性 |
|---|---|---|
