## 三、协作约定（硬规则）

### 3.1 先问再做

动手前用一两句话说清要改什么、为什么、影响哪些文件，**等确认再执行**。
只读操作除外。

**新增/修改文件、装依赖、改配置、push，都算"做"。**

### 3.2 高危单独确认

删文件、装依赖、改全局配置、`push --force`、动系统设置 —— 单独问一次。

### 3.3 不要让他脱节（本项目核心）

**每次交付必须包含三件套**：

1. **这是什么**：一句话说清改了哪层（听/转/想/做）
2. **怎么验证**：他自己能跑的一条命令 + 期望看到什么
3. **坏了看哪里**：按症状指向具体文件或命令

**另外**：

- **一轮只讲一个概念**。多个概念要分成多次。
- 遇到黑盒（VAD/Whisper/CUDA），**给可用路径，不强制解释内部**。
  他问就讲，不问就当作"能用的零件"。
- **不要因为"更优雅"就重构**。他看不懂的优雅等于负担。
- 出现卡点先问"你现在看到什么"，**不要一次性猜 5 个原因**。

### 3.4 教测试方法，不要代跑全部

他明确说过"你的测试节奏太快"。**优先给命令让他自己跑**，
只在需要判断"这算不算通过"时才替他分析输出。

### 3.5 让他有参与感

他要自己写一部分。**不要一次把功能全做完**，
留明确的空白给他填（比如 `# TODO: 这里你自己写`）。

## 五、他已经踩过、别再让他重踩的坑

| 坑 | 表现 | 结论 |
|---|---|---|
| `.bat` 用 LF 换行 | `'IAO72' 不是内部或外部命令` | 批处理必须 CRLF，已写入 .gitattributes |
| PowerShell 写文件带 BOM | git 报 `not a valid attribute name`；Python 部分工具解析失败 | 写文件一律无 BOM |
| 系统默认麦克风是虚拟设备 | 录到 -96 dBFS 全静音 | 必须做设备活体检测 |
| 同一设备不同采样率有的死 | 48k 有声音，44.1k 全零 | 逐个采样率试 |
| `sd.rec` 开头 0.2~0.3s 是空的 | 短时长测量恒判"设备死" | 测量必须掐头 |
| Silero VAD v5 要 64 点上下文 | 概率最高只有 0.08 | 输入 576 点而非 512 |
| VAD pre-roll 太短 | "亮度"→"量都" | 800ms |
| venv 少装依赖 | 串口静默失败进入 DRY-RUN | 装完库要实际跑一遍链路 |
| `py` 与 `python` 不是同一个解释器 | ModuleNotFoundError | 一律用 venv 的绝对路径 |

## 六、他真正想要的

不是"一个能跑的 demo"，而是：

> 一个**自己知道每块在干什么、出问题能定位**的系统，

**所以**：
- 交付时多说"这块在数据流的哪个位置"
